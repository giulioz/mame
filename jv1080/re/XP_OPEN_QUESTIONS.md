# Roland XP Chip Emulation — Open Questions Reference

## 1. Emulation status

The Roland XP PCM+DSP device (`ROLAND_XP`, MAME `roland_xp_device`, declared `device_rom_interface<27>`) currently models a **SCCore-faithful but silicon-unverified PCM voice engine**: 64-voice DPCM streaming, the 4-tap cumulative-delta interpolator, the five log/linear/trunk ramp generators (pitch, amp, amp-mod, TVF-F, TVF-Q), a Chamberlin-style state-variable TVF, and the host register/IRQ/command-busy plumbing all reproduce SCCore's float reference math reinterpreted in fixed point — but essentially none of it has been checked against a real chip, and several arithmetic choices (decode scale, accumulator width, rounding/saturation, control cadence) are deliberate approximations or unresolved contradictions between the two primary RE docs. The **DSP/effects path is essentially unemulated**: PRAM/CRAM/IRAM/ERAM (`0x2C00–0x38FF`) are passive byte storage, no opcode is ever decoded or executed, all 64 mixer buses are computed then discarded, and `sound_stream_update` fakes output by summing only sends 0/1 directly to stereo with a placeholder `1<<21` scale. Consequently the device ships `MACHINE_NOT_WORKING | MACHINE_NO_SOUND`, and — critically — the SCCore oracle that anchors the voice/DSP work is the SC-88Pro's `scgsMasterPram`, a **different microcode program** from the JV-1080's 40 RFX algorithms and paired-tone ring-mod, so it can validate the opcode engine but never the JV's actual effect output.

## 3. Open questions by subsystem

### 3.1 Voice engine (DPCM decode, addressing, loop modes)

- **Wave-ROM stream format (interleaved vs dual-stream)** — *known:* `decode_sample` reads mantissa @ `sample_addr`, exp nibble @ `sample_addr>>5` selected by `BIT(addr,4)` (`roland_xp.cpp:1109-1123`); *unknown:* whether silicon uses SCCore's separate `+0x20`/`+0x38` pointers. (hardware-trace, **high**)
- **Address units: bytes vs samples; shift-stream co-location** — *known:* one address unit = one delta byte, exp indexed at 1/32 rate via `>>5`; loop/start/end masked to `0xfffff` (`roland_xp.cpp:1114-1176`); *unknown:* whether start/loop/end registers are delta-byte or decoded-sample units, and whether the `>>5` shift stream truly shares the delta address space (contradicts SCCore's `+0x38`). (hardware-trace, **high**)
- **DPCM history form: raw deltas + cumulative LUT vs four absolute samples** — *known:* `do_voice` folds deltas into `v.dpcm_val`, feeds `interp_lut` cumulative basis (`roland_xp.cpp:14-18,1186-1225`); *unknown:* whether the algebraic identity holds for all overflow counts 0/1/2/3/≥4 and the partial-overflow stale-history case. (emulator-experiment, **high**)
- **Decode fixed-point scale** — *known:* MAME deliberately uses `(10-exp)&0xf` + `mantissa<<11`, *not* SCCore's `exp+10` / `2^-27` (`roland_xp.cpp:1118-1122`); *unknown:* the real accumulator width, exact shift, and saturation point. (hardware-trace, **high**)
- **Integer DPCM accumulator width/overflow** — *known:* `v.dpcm_val` is int32 with `add_wrap_s32` (`roland_xp.cpp:1088-1091,1196`); *unknown:* whether silicon wraps, saturates, or is narrower — SCCore's float path can't distinguish. (hardware-trace, medium)
- **Shift-block phase after loop/reverse** — *known:* MAME derives the shift nibble from `sample_addr` bits, no independent block counter (`roland_xp.cpp:1114-1122`); SCCore repositions `+0x44` metadata explicitly on loop jump; *unknown:* whether block phase keys on absolute address or an independent per-voice counter that can desync at loop wrap/reverse. (sccore-diff, **high**)
- **Reverse playback of the delta integrator** — *known:* `advance_sample_address` honors `BIT(wave_ctrl,11)` reverse by decrementing, but `decode_sample` reconstructs via a forward integrator (`roland_xp.cpp:1142,1165-1168`); *unknown:* how the chip reconstructs reverse-played compressed waves (pre-decode block? negate deltas? unused?) — SCCore has `Run_*R` variants not transcribed. (firmware-re, **high**)
- **One-shot selection rule (loop==end)** — *known:* `one_shot = (loop_start==loop_end)`, `alt_loop = BIT(wave_ctrl,12)` (`roland_xp.cpp:1143-1149`); *unknown:* whether silicon terminates on loop==end or a distinct mode bit — SCCore never calls the one-shot Run entry points, so they're unvalidated. (hardware-trace, **high**)
- **Alternating-loop turnaround off-by-one** — *known:* `alt_loop_dir` toggles at boundaries via exact equality (`roland_xp.cpp:1150-1171`); *unknown:* whether endpoint samples play once or twice and the exact pivot address — produces periodic click/buzz if wrong. (sccore-diff, medium)
- **Loop boundary: exact-equality vs crossing** — *known:* `at_boundary` uses `((compare^address)&0xfffff)==0`, relying on step always = 1 (`roland_xp.cpp:1150-1151`); *unknown:* whether hardware uses `>=`/crossing, which would differ if loop length isn't step-aligned or under reverse. (hardware-trace, low)
- **Wave-ROM bank width: 4-bit (JV) vs 7-bit (SCCore)** — *known:* `rom_high = (wave_ctrl&0x0f)<<20`, bits 4-6 treated as non-address to avoid a retrigger bug (`roland_xp.cpp:1112-1114`); *unknown:* true address width and role of bits 4-6 on the JV specifically. (hardware-trace, medium)
- **Voice loop event → IRQ reason mapping** — *known:* `do_voice` returns `voice_event` on loop entry; raised once as reason 5 via `loop_irq_pending` (`roland_xp.cpp:1153-1176,1267-1271`); *unknown:* whether the on-bus code is 5 (JV firmware) or SCCore's `_InterruptRequest(2)`, and once-vs-every-loop policy. SCCore latches on `CEPTGVoice+0x48` **bit4**; MAME uses bit6 (IMPLEMENTATION_GAPS:21). (firmware-re, medium)
- **Pitch-zero gates whole voice vs only sample advance** — *known:* `pitch_to_increment` returns 0 for `pitch_val<=0`; `output_i==0 → continue` skips per-sample (`roland_xp.cpp:110-111,1262-1263`); *unknown:* whether the chip still decays amp/TVF or fires loop IRQ at pitch 0, and per-sample vs once-per-quantum active sampling. (sccore-diff, medium)

### 3.2 Interpolators & envelopes (ramp generators, cadence)

- **flag_type {2,0,4,4} vs {0,2,4,4}** — *known:* emulator `{2,0,4,4}`, pipeline/GAPS agree; *unknown:* SCCore RE doc:1081-1083/1114 says `{0,2,4,4}` — unreconciled direct contradiction on which value selects linear vs log (`roland_xp.cpp:128-136`). (sccore-diff, **high**)
- **Log update: minimum-magnitude floor vs ±1024 clamp** — *known:* `interp_update_log` forces a *minimum* magnitude 1024 step via two unsigned compares (`roland_xp.cpp:246-263`); *unknown:* SCCore RE doc:1130 says `clamp(delta,-1024,+1024)` — the *opposite* (max saturation). Also the `int16(error>>13)` narrowing is undocumented. Min-vs-max flips the final-approach curve. (sccore-diff, **high**)
- **Truncation (trunk) algorithm** — *known:* `interp_update_trunk` is a stateful two-branch damper seeded `aux=current/2`, target=0, doesn't clear active on one branch (`roland_xp.cpp:265-288`); *unknown:* SCCore RE doc:1136-1142 gives a simpler model that does **not** match; trunk is the fast-damp/voice-steal path (`XPsetFastDamp`) so wrong edges cause clicks/stuck voices. (sccore-diff, **high**)
- **Start vs SetNewDist inferred from register address** — *known:* writes to start-value banks (`0x1B00-0x1E00`, `0x2100`) map to `reload_*`; destination banks (`0x1100-0x1A00`) to `retarget_*` (`roland_xp.cpp:981-998`); *unknown:* SCCore carries this as an explicit boolean (`XPsetToXpByTrig`/`ByServ`); whether the chip restarts on a start-bank write or a separate strobe is unverified and depends on the unknown bus write protocol. (hardware-trace, **high**)
- **Interval counter clocked per Run vs per audio sample** — *known:* `interp_tick_due` increments once per `Run` call, masked by `{0,0x07,0x1f,0x7f}` (`roland_xp.cpp:224-228`); *unknown:* SCCore RE doc:1105/1149-1156 says increments each sample (32 kHz). Sets absolute envelope/sweep/portamento rates. (hardware-trace, **high**)
- **Linear minimum-step asymmetry** — *known:* `+1` floor only on ascending; descending zero-step intentionally left to hang until retargeted (`roland_xp.cpp:183-244`); *unknown:* whether silicon has the same/different/no descending floor (GAPS:17 — "copy exactly"). Affects whether segments complete and segment-completion polling advances. (sccore-diff, medium)
- **Pitch granularity (8 samples/value) & 32-sample batching visibility** — *known:* one pitch update per `control_tick_8`, pitch always runs (`roland_xp.cpp:1260-1261`); *unknown:* whether 32-sample batching is a real chip feature or SCCore software batching (pipeline:45 "not established"). (hardware-trace, medium)
- **CInterpAM free-running counter** — *known:* `interp_update_am` ticks unconditionally even after active clears; `retarget_ampmod` doesn't reset counter/aux (`roland_xp.cpp:322-328,417-425`); *unknown:* whether the post-retarget sub-tick phase matches silicon. (sccore-diff, medium)
- **Amp retarget leaves trunk aux/target stale** — *known:* `retarget_amp_interp` only recomputes step for linear mode (`roland_xp.cpp:405-415`); *unknown:* whether mid-flight retarget into trunk is a real firmware op and what the chip does with trunk aux state. (sccore-diff, medium)
- **interp_lut provenance & rounding** — *known:* cumulative basis `{c1+c2+c3, c2+c3, c3}`, `>>12` per tap (`roland_xp.cpp:18-45,1220-1225`); *unknown:* whether derived from exact Q12 kernel (with SCCore's spurious `1e-5` c3 zeroed) or carries float rounding, and whether `>>12` matches chip rounding. (emulator-experiment, low)
- **Phase fraction width for row selection** — *known:* `interp_ratio = (old_subphase>>9)&127` from a 16-bit subphase (`roland_xp.cpp:1182`); SCCore agrees (`>>9`, 7 bits); *unknown:* whether the accumulator is exactly 16 bits and whether sub-bit-9 dithering exists. (hardware-trace, low)
- **interp_q14_output `>>3` rounding/sign/saturation** — *known:* returns `int16_t(current>>3)` (`roland_xp.cpp:149-152`); *unknown:* arithmetic-shift vs truncate-toward-zero vs round, and int16 wrap-vs-saturate at extremes; SCCore's `1e-5` zero floor's hardware counterpart. (sccore-diff, low)
- **Pitch→increment table `/257` + forced endpoint** — *known:* `s_log_table[257]` = `floor(2^17·2^(i/257))`, entry 256 forced to `2^18`, signed-round + octave shift `~(pitch>>14)&0xf` (`roland_xp.cpp:49-126`); *unknown:* whether the chip stores a 14-bit-truncated (`value>>4`) ROM, the rounding mode, and the reason for the forced endpoint (pipeline:263 "unknown"). (firmware-re, low)
- **TVF-Q `>>2` prescale & TVF-F log→linear domain** — *known:* `reload_tvf_q` seeds `tvf_q_start_val>>2`; TVF-F start/dest run through `pitch_to_increment` at setup (`roland_xp.cpp:367-385,437-443`); *unknown:* whether the chip interpolates TVF-F in linear (octaves) or log domain and whether `Q>>2` is a real register-width difference. (sccore-diff, medium)
- **TVF-Q frequency limiter table** — *(see TVF section; cross-cut)*. (firmware-re/sccore-diff, medium-**high**)

### 3.3 TVF (state-variable filter)

- **F-limiter table size/contents/index** — *known:* `limit_tvf_frequency` synthesizes a **1024-entry** Chamberlin-stability table `floor((sqrt(q²+4)-q)·16384)` indexed `q.current>>8` (`roland_xp.cpp:154-173`); *unknown:* pipeline §8 says a **16-entry** `FLimitter_float` indexed by Q state; SCCore RE doc never describes any F-limiter; `hack_scva/xp.cpp` applies **none**. All sources disagree. Wrong table → premature dullness or SVF blow-up at high Q. (sccore-diff, **high**)
- **TVF→TVA vs TVA→TVF order** — *known:* device runs SVF then amp/ampmod, hedged (`roland_xp.cpp:1229-1235`); reference does the opposite; *unknown:* which order silicon uses and whether product-dependent. (sccore-diff, **high**)
- **Cutoff coefficient `f` derivation & Q14 shift** — *known:* device converts via `pitch_to_increment` once at setup, then `>>3` (`roland_xp.cpp:149-152,377-384`); reference runs `pitch_to_increment` per-sample and uses `>>4`; *unknown:* setup-vs-per-run timing and `>>3` vs `>>4` (an octave). (sccore-diff, **high**)
- **Resonance coefficient `q` scaling** — *known:* device uses `q_q14 = tvf_q_interp.current>>3` (`roland_xp.cpp:149-152,1227`); reference uses raw `q_val` (no shift); *unknown:* correct Q14 mapping of the log-domain CInterpQ output — sets resonance amount and self-oscillation threshold. (sccore-diff, **high**)
- **Filter-type register decode (HPF/BPF swap + override)** — *known:* `decode_filter_type` maps bits 10:11 through `type_map={0,2,1,3}` (swaps HPF↔BPF) plus a `0xf000` override reading `tvf_q_interp_ctrl` (`0x1600`)&3 (`roland_xp.cpp:175-181`); *unknown:* SCCore RE doc:441-446 says direct `0→LPF,1→HPF,2→BPF,3→PKG`; reference uses raw `(data>>10)&3`, no remap/override. All three disagree — a swap error makes HPF patches sound bandpass. (sccore-diff, **high**)
- **Q27 multiply rounding/width/saturation** — *known:* `mul_q27_q14` is `(int64·)>>14` truncating toward −∞, per-step `sat_q27` to `[-0x08000000,0x07ffffff]` (`roland_xp.cpp:1074-1098`); *unknown:* chip's rounding mode, real intermediate width (pipeline §8 notes the `f*bp` Q41 intermediate truncated to Q27), and where saturation clamps inside each of the three SVF steps. (hardware-trace, medium)
- **TVF-F/Q register range endpoints** — *known:* `tvf_f_destination_val` annotated `max 0x3c000 / min 0x14000`, `tvf_q_destination_val max 0x80000`, Q start `>>2` (`roland_xp.h:100-105`); *unknown:* whether these are exact silicon limits or empirical. (hardware-trace, medium)
- **PKG output order of operations** — *known:* mode 3 returns `sat_q27(lp_q27 - hp_q27)` from already-saturated states (`roland_xp.cpp:1104`); *unknown:* whether the chip uses `lp-hp` or the unsaturated `2·lp + q·bp - input` form — diverges once intermediates clamp. (sccore-diff, low)
- **Filter state init (zero vs 1e-5)** — *known:* `tvf_bp/tvf_lp` cleared to 0 (`roland_xp.h:115-116`); *unknown:* SCCore seeds `~1e-5` purely as a denormal dodge (documented software artifact); confirm silicon resets to exactly zero. (hardware-trace, low)

### 3.4 Mixing & bus routing

- **Dry/effect sends bypass all 64 buses** — *known:* device accumulates into `buses[64]` then ignores it, summing only send 0→`dry_left`, send 1→`dry_right` (`roland_xp.cpp:1272-1291`); *unknown:* how voices reach master L/R on hardware — SCCore routes dry to 58/59 and sums via the DSP; JV comment says dry lands on 10/11. THE reason the chip is faithful-`NO_SOUND`. (firmware-re, **high**)
- **Send bus number ignored; JV bus roles unverified** — *known:* `bus = send_word&0x3f` decoded but output keys on **slot index** 0/1, not the decoded bus (`roland_xp.cpp:1274-1283`); *unknown:* what the JV firmware programs into the 6-bit bus field; the SC-88Pro bus-role table (58/59 dry, 60 reverb, 51 EQ, 16-48 intermediate, ring-mod) may not transfer to the JV. 10/11 vs 58/59 unresolved. (firmware-re, **high**)
- **Voice-engine output never reaches speakers even as dry-bypass** — *known:* dry sum depends on sends 0/1 carrying audible level, but JV programs the DSP graph for buses 10/11 (`roland_xp.cpp:1272-1291`; firmware-map:369-371); *unknown:* whether sends 0/1 actually carry level on the JV — the bypass may be legitimately near-silent even with perfect voices, masking whether the voice engine works. (sccore-diff, **high**)
- **5th (Reverb?) send bank vs wave-ROM aperture overlap** — *known:* `NUM_MIXER_SENDS=4`, `0x3C00-0x3FFF` = wave-ROM aperture (`roland_xp.cpp:875-902,1056-1071`); *unknown:* `xp_regs.md:71` lists a 5th per-voice send at `0x3C00-0x3C7F` ("Send: Reverb?", init-only) overlapping the aperture — device can't have both. (hardware-trace, medium)
- **Send gain scale `>>10` (/1024) linear vs log** — *known:* `level = send_word>>6` (10-bit), `contribution = (voice·level)>>10` (`roland_xp.cpp:1274-1278`); *unknown:* whether the 10-bit field is linear `gain/1024` or log/table-mapped (envelope params are log-domain, so log coding is plausible), and per-bus saturation. (sccore-diff, medium)
- **Per-bus chorus/delay send-gain arrays not modeled** — *known:* SCCore applies `mfSendGainCho`/`mfSendGainDel` to buses 16-48 (pipeline:404-409); device never reads buses 16-48; *unknown:* their values/source/timing and whether they're a chip facility or SCCore-side. (firmware-re, medium)
- **Bus accumulator width/saturation** — *known:* shared `std::array<int64_t,64>`, only final `dry_left/right` saturated (`roland_xp.cpp:1244-1290`); *unknown:* whether silicon accumulates in wide integer (what width) or float (SCCore) and whether per-bus clamping occurs. (hardware-trace, low)
- **Block-batching vs per-sample mixing** — *known:* device mixes one sample at a time with `m_control_phase&7` (`roland_xp.cpp:1240-1292`); *unknown:* whether send-gain updates are latched per 32-sample block on silicon. (hardware-trace, low)
- **Final output scale `1<<21`** — *known:* arbitrary placeholder normalizer (`roland_xp.cpp:1289-1290`); *unknown:* the real DAC/output-format full-scale — stands in for an entire unknown output stage, not just a gain (see 3.9). (emulator-experiment/hardware-trace, low)
- **IRAM3 breakpoint gain `× scale × 2`, Q22 vs Q15** — *known:* device models `target=(value&0x1ff)<<13` (Q22) vs SCCore `<<6` (Q15), rate `0x300`, per-quantum doubling (`roland_xp.cpp:566-605`; pipeline:415-433 "needs a bus trace"); *unknown:* whether the host word is Q22, the `×2` final scale, and the `0x300` time constant match silicon. (hardware-trace, medium)

### 3.5 DSP ISA & effects

- **No PRAM interpreter exists** — *known:* `0x2C00-0x38FF` is pure storage; nothing decoded/executed (`roland_xp.cpp:1013-1027,1286-1290`); *unknown:* the entire bytecode interpreter — opcode semantics, accumulator/store/pipeline behavior (`xp_dsp_isa.md:340-349` "execution hypothesis"). (emulator-experiment, **high**)
- **JV microcode ≠ SCCore oracle program** — *known:* SCCore is SC-88Pro `scgsMasterPram` (SCCore RE doc:761-781); *unknown:* the JV's 40 RFX algorithms, ring-mod, and reverb/chorus/delay microcode are absent — the oracle validates only the opcode engine. (sccore-diff, **high**)
- **ALU opcode semantics (0,5,7,B,D,F)** — *known:* only six nibbles occur in JV slots; analyzer prints CSP analogies (MAC.A/CMP.A/NEGMAC.A/DMAC.B/VMUL.B/VMAC.B) explicitly labeled non-XP (`analyze_dsp_bytecode.py:28-33,240`; `xp_dsp.md`); *unknown:* actual operation/operands/accumulator effect — CSP coefficient-selector rules demonstrably don't apply (opcode-F carries full `0x5000`). (emulator-experiment, **high**)
- **PRAM upper-half fields (31:16)** — *known:* split into `p-mem` 27:21, `p-ctl` 20:16, selector codes 8-11/4-7 (`xp_dsp_isa.md:43-66`); *unknown:* read/write/bank/saturation/scaler selects, parallel-channel/ERAM-fragment overlap, scaler bits 25:24 — active even when low store field is zero. (sccore-diff, **high**)
- **Store-mode 3-bit table (11:9)** — *known:* `none/synth-bus/special.A[.sat]/iram.A|B[.sat]` borrowed from CSP (`analyze_dsp_bytecode.py:39-48`); *unknown:* whether XP's store encoding, saturation, and A/B IRAM-bank distinction match CSP — decides where each result lands. *Note:* unlike the CSP/ESP, the XP needs **no store-to-host** instruction for observation — the hardware exposes every IRAM/PRAM/CRAM location on demand via the `0x3910/0x3912` readback register (`XP_HARDWARE_DEBUG.md §6.2`), so a probe just stores to IRAM1/2 and the host reads it back. This does **not** resolve the store-*mode* encoding itself (where in the DSP a store lands), which remains the open item here. (emulator-experiment, **high**)
- **9-bit memory/special-register selector map** — *known:* low 9 bits select IRAM/special-reg; fragments guessed (`0x0a/0x0b` audio-in?, `0x15/0x16` audio-out?) (`xp_dsp.md:10-31`; `xp_dsp_isa.md:346-349`); *unknown:* full selector→resource map (IRAM bank/word, synth input bus, output bus, special reg, audio I/O). Blocks connecting DSP to the 64 buses. (sccore-diff, **high**)
- **ERAM address op/mode bits & commit latency** — *known:* 16-bit address split 7+9 across adjacent PRAM words (`decode_eram_address`, proven via `xp_dsp_write_eram_offset` @ firmware `0x0a00225c`) (`analyze_dsp_bytecode.py:102-114`); *unknown:* operation type, circular-buffer base, commit latency, variable-offset/read-vs-write modes (`xp_dsp_isa.md:114-115`). - **Register dumps non-deterministic, high byte discarded** — *known:* `dump_regs.py` stores only `val&0xFF`; `dump.bin` vs `dump2.bin` differ at ~53 positions, mostly `0x00↔0xFF` floating-bus flips plus structured diffs at `0x3918/0x3919/0x391c` + `0x40`-stride mirrors (`dump_regs.py:24-31`); *unknown:* whether the diffs are live state or noise — the only direct register observation. (hardware-trace, medium)
- **Arduino bus timing uncalibrated, no DTACK/ready** — *known:* fixed 9-nop (~0.56 µs) delays, CS faked by toggling A17 (`bus_probe.ino:66-74,99-131`); *unknown:* real setup/hold/access-time and whether A17-as-CS glitches adjacent pages — likely explains the non-deterministic dumps. (hardware-trace, medium)
- **Fixed-point widths/rounding/saturation never measured** — *known:* specific Q14/Q27, `sat_q27`, round-away-from-zero, `>>13`/`>>6` choices (`roland_xp.cpp:566-605,1074-1123`; GAPS item 1 "not established"); *unknown:* the silicon arithmetic at every boundary — SCCore is float, chip is fixed-point. (hardware-trace, medium)

### 3.10 Cross-cutting

- **External effect DRAM size: 256 KB (device) vs 128 KB (driver) vs 1 MB (SCCore LSP)** — *known:* `DRAM_SIZE=0x40000` (header calls it "2Mbit"), driver comment "1 Mbit (128 KB)" is the SH7034's *own* DRAM, SCCore `fEramBuf`=256 KB but `CCirBuf`=1 MB (`roland_xp.h:63`; `roland_jv1080.cpp:22`; SCCore RE doc:1335,2088); *unknown:* the XP's real effect DRAM size — Triple/Quadruple-Tap and Gate Reverb need large ERAM tap tables that would alias if 256 KB is wrong. (hardware-trace, medium)
- **Wave-ROM address-width contradiction: 24-bit/8-CS (header) vs `<27>` interface vs 20-bit decode mask** — *known:* header says 24-bit/8-CS; device is `device_rom_interface<27>`; aperture composes 27 bits; `decode_sample` masks to 20 bits + 4-bit bank = 24-bit reach (`roland_xp.h:10-14,33`; `roland_xp.cpp:892-901,1109-1123`); *unknown:* the true width — the streaming path (24-bit) can't reach the same space the aperture (27-bit) can; expansion samples above 16 MB may be unaddressable. (hardware-trace, medium)
- **32 kHz internal rate = clock/768 unverified divisor** — *known:* `m_rate = clock()/768`, driver clocks XP at `24.576_MHz_XTAL` (`roland_xp.cpp:613`; `roland_jv1080.cpp:641`); *unknown:* whether the XP derives 32 kHz by /768 and the exact crystal/divider chain — a wrong master rate detunes everything uniformly. (hardware-trace, medium)
- **Control-cadence doc contradiction: per-sample (32 kHz) vs per-8-sample (4 kHz)** — *known:* reconciled model + emulator use base divisors `{1,8,32,128}`, pitch/8 (`roland_xp.cpp:1247-1248`); *unknown:* SCCore RE doc:1149-1156 gives base `{0,8,16,24}` masks `{0,0x07,0x1F,0x7F}` and "every sample (32 kHz)" for pitch — an 8× temporal-resolution disagreement between the two SCCore-derived docs (overlaps 3.2/3.7 interval-counter item). (sccore-diff, medium)
- **`0x391c`/`0x3930` EFX-delay self-calibration probes DRAM timing** — *known:* `0x3930` = calibration drive (`step<<5`), `0x391c` = comparator (factory reads bit 6) (`xp_firmware_map.md:339,344`); *unknown:* together they form an external-DRAM delay self-calibration loop — the chip may measure real DRAM latency at boot to set delay-line lengths; neither register nor DRAM timing is modeled. (firmware-re, low)
- **Power-on/reset state assumed all-zero** — *known:* `device_reset` zero-fills `m_reg/m_dsp_program/m_dram/m_global_config`, seeds reset bitmap `0xff` and random seeds (`roland_xp.cpp:740-767`); *unknown:* whether silicon powers up zeroed vs garbage, and whether the LFSRs power up to `0xefa6/0x9c23` (SCCore software constants) vs firmware-seeded vs free-running — the `4f95,4b65,…` sequence depends entirely on the seed-at-reset assumption. (hardware-trace, low)
- **Save-state: `m_reg` vs `m_voices` duplication, mid-ramp/mid-DPCM restore** — *known:* both raw bank words and decoded per-voice mirrors saved separately, no re-derivation on load (`roland_xp.cpp:619-731`); *unknown:* whether a loaded state resumes mid-ramp / mid-DPCM-block / mid-IRAM3-breakpoint correctly; the driver's parallel `m_xp_regs` debug shadow consistency is unchecked. (emulator-experiment, low)
- **Expansion (SR-JV80) / PCM-card address space unrepresented** — *known:* board scanner @ `0x0a00a1b0` classifies banks (internal bank 0 = INT100A); driver loads only 4 internal 2 MB ROMs into region `xp` (`xp_firmware_map.md:358-365`; `roland_jv1080.cpp:658-663`); *unknown:* how expansion boards/cards map into the wave-ROM space and how the 4-bit (JV) vs 7-bit (SCCore) bank reconciles across populated slots. (firmware-re, low)
- **Final output scale `1<<21` stands in for an unknown DAC/output stage** — *known:* arbitrary placeholder; SCCore's SRC is software-only (`roland_xp.cpp:1289-1290`; pipeline:435-459); *unknown:* the chip's output format (serial-to-external-DAC? on-chip DAC? word width?) and therefore absolute 0 dBFS — even a correct mix is at the wrong amplitude. (hardware-trace, low)

## 4. What would most move the needle

1. **Capture the XP's external buses with a logic analyzer — wave-ROM and INT first.** A single capture of the wave-ROM address/data lines during a known note simultaneously resolves the #1 blocker (stream format: interleaved vs dual `+0x20`/`+0x38`, address units, shift-block cadence, bank width) and lets a captured ROM image be round-tripped through `decode_sample`. Capturing INT in the same session resolves the IRQ assertion/format/ack/reason-4-7-8 questions (#7) that gate the firmware's voice scheduler and the eventual DSP-commit path. The existing register-only Arduino probe cannot reach either bus and its non-deterministic dumps and missing `~UWR` strobe mean it cannot even be trusted for the register space — so a proper analyzer + full-width host writes is the prerequisite for almost every other hardware-trace item.

2. **Build a PRAM interpreter from the now-decoded ISA and validate it against the factory EFX oracle.** UPDATE (2026-07): the instruction set is decoded on hardware (JV debug ROM) — field split `[15:14] st | [13:6] word | [5:0] column`, single 24-bit saturating accumulator, read (`st1 col0` = `acc+=mem[addr14]`), MAC (col 0x15), add-const (col 0x0F), load (col 0x1F), store (st3, bank map) all confirmed (`xp_dsp_isa_decoded.md`, `XP_FACTS.md` C22–C31). So the interpreter is now a matter of implementing the confirmed ISA, and the factory test (seed IRAM3[0:3]=`00/55/aa/ff`, write 4 to `0x3916`, expect them in IRAM3[4:7] after `0x208` ticks) becomes a validation oracle rather than the means of discovery. Remaining ISA gaps: st0/st2 verbs, full column table (mem≠0), ERAM/DRAM page addressing.

3. **Get one hardware audio recording of known voice parameters, and pin the dry-bus routing.** Without a ground-truth recording, no amount of SCCore matching proves fidelity, and the dry-bypass (sends 0/1 → stereo) may be legitimately silent if the JV's audible path is buses 10/11 (#9) — meaning today's silence can't distinguish "voice engine broken" from "wrong sends bypassed." A recording plus a firmware trace of which 6-bit bus field the JV programs into each send would confirm the voice engine end-to-end and unblock the entire mixing/output-topology section, including the DIRECT 1/2 pairs the factory test exercises.
